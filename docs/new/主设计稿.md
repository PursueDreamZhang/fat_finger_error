# 期货乌龙指日线初筛器设计稿

> 本设计稿描述第一版重写方案，只约束新的系统设计，不以现有代码实现为前提。

## 1. 目标与边界

### 1.1 核心目标

第一版系统的目标非常明确：

- 用户输入若干个期货品种编码，例如 `AU`、`JD`
- 用户输入开始日期和结束日期
- 系统自动分析这些品种在该时间区间内的日线数据
- 输出这些品种的 `疑似乌龙指可疑日期`
- 生成一个适合人工查看和交互的 `HTML 报告`

### 1.2 主输出与次输出

第一版系统的输出优先级如下：

1. `HTML 可疑日期分析报告`
2. `可疑日期明细表`
3. `品种级汇总统计`

其中：

- HTML 报告是主输出
- CSV / JSON / DataFrame 是辅助输出

### 1.3 非目标

第一版系统明确不做以下事情：

- 不直接认定某笔或某天一定是乌龙指成交
- 不做分钟级或逐笔级确认
- 不区分夜盘跳空和日盘盘中错单
- 不复现交易所错单认定规则
- 不把“年度风险评分”作为第一目标

### 1.4 系统定位

第一版系统的正式定位为：

- `基于日线数据的疑似乌龙指可疑日期初筛器`

更具体地说：

- 它是一个“找候选日期”的工具
- 不是一个“直接给出乌龙指确认结论”的工具

## 2. 用户工作流

系统必须围绕最终使用方式设计，而不是围绕内部 DataFrame 接口设计。

### 2.1 用户输入

用户输入只有三类：

- `symbols`
  - 品种编码列表，例如 `["AU", "JD"]`
- `start_date`
  - 开始日期，例如 `20240101`
- `end_date`
  - 结束日期，例如 `20251231`

### 2.2 系统内部处理流程

在用户输入上述参数后，系统自动完成以下步骤：

1. 根据品种编码识别该品种在时间区间内涉及的合约
2. 获取相关合约的日线数据
3. 获取或构造合约元数据
4. 自动选择主参考合约并构造同日活跃合约集合
5. 进行样本过滤
6. 进行候选评分
7. 产出可疑日期结果
8. 生成 HTML 报告

### 2.3 用户最终看到的结果

用户最终最关心的是：

- 某个品种有哪些日期可疑
- 哪个合约在这些日期最可疑
- 为什么可疑
- 可疑程度高低如何

而不是先看一堆内部中间表。

## 3. 输入设计

### 3.1 用户层输入

系统对外暴露的主入口参数为：

- `symbols: list[str]`
- `start_date: str`
- `end_date: str`

可选参数可以后续扩展，但第一版不强制加入。

### 3.2 系统内部输入

系统内部仍然需要两类数据表，但它们不是用户手工准备的输入，而是系统自动构造的中间数据：

- `daily_bar`
- `contract_meta`

#### 3.2.1 daily_bar

最小字段包括：

- `trade_date`
- `commodity`
- `contract`
- `open`
- `high`
- `low`
- `close`
- `pre_close`
- `volume`

#### 3.2.2 contract_meta

最小字段包括：

- `commodity`
- `contract`
- `listed_date`
- `last_trade_date`
- `delivery_month`

### 3.3 数据访问层要求

第一版必须明确存在一个 `数据访问层`，负责：

- 根据 `symbols + 时间区间` 找到相关合约
- 拉取这些合约的日线数据
- 提供合约元数据

设计上不允许把“daily_bar 已经准备好”当成唯一运行前提，否则系统无法满足最终使用方式。

第一版数据源策略固定为：

- `Tushare` 负责合约发现
- `Tushare` 作为默认主数据源，负责日线拉取与元数据补全
- 当 `Tushare` 调用失败时，先重试 `2` 次
- 若 `2` 次重试后仍失败，再切换到 `AKShare`
- `AKShare` 作为备用数据源，负责日线拉取与部分元数据补充

第一版的默认优先级固定为：

1. `Tushare`
2. `AKShare`

不允许同时并行混用两套数据源，也不允许在没有失败重试的情况下直接跳过 `Tushare`。

### 3.4 品种编码到合约集合的映射规则

这是第一版必须先固定的规则，否则后续所有分析都会漂移。

对于用户输入的每个品种编码，例如 `AU`、`JD`，系统必须按固定步骤确定本次分析的合约集合：

1. 获取该品种在分析区间附近可能存在的所有候选合约
2. 过滤掉在 `[start_date, end_date]` 内没有任何日线记录的合约
3. 过滤掉在分析区间内完全无成交或几乎无成交的合约
4. 将剩余合约作为该品种本次分析的有效合约集合

这一步至少要输出两个内部结果：

- `commodity_contracts_map`
  - 每个品种对应的有效合约列表
- `contract_availability`
  - 每个合约在分析区间内的有效覆盖情况

如果这一步没有被设计成独立规则，而是在实现时临时拼接，主参考选择、邻近参考选择和生命周期过滤都会不稳定。

第一版在这一步优先使用 `Tushare fut_basic`，因为它直接提供：

- 合约列表
- 上市日期
- 最后交易日期
- 交割月份

只有当 `Tushare` 连续失败时，才允许回退到 `AKShare` 的相关接口和本地补充逻辑。

## 4. 核心结果定义

### 4.1 主结果：可疑日期

第一版最核心的结果是：

- `疑似乌龙指可疑日期`

定义为：

- 某个品种下的某个合约，在某个交易日出现了明显异常的日线形态与结构失真特征
- 且在经过样本过滤与 `A/C/E` 评分后，仍值得人工进一步查看

### 4.2 附加结果：品种级汇总

除了可疑日期明细，系统还应输出品种级统计，例如：

- 某个品种在本次分析区间内共命中多少个可疑日期
- 哪些合约最容易触发候选
- 最高分的若干可疑日期是什么

这部分是辅助结果，不是主目标。

### 4.3 不作为第一版主结果的内容

以下内容不再作为第一版核心交付物：

- 年度风险评级
- 正式年度风险得分
- 跨年份比较体系

如果后续需要，可以在第二版加回，但不应压过“可疑日期输出”和“HTML 报告”。

## 5. 参考合约设计

### 5.1 主参考合约

第一版固定定义为：

- `主参考合约 = 当日同品种活跃合约中成交量最大的合约`

原因：

- 不依赖外部主连口径
- 规则语义稳定
- 方便解释

### 5.2 同日活跃合约集合

第一版不再单独固化“邻近参考合约”字段。

实现中仅保留：

- `主参考合约`
- 同日活跃可分析合约集合

其中同日活跃可分析合约集合用于：

- 形成 `peer` 中位数基线
- 计算 `active_peer_count`
- 支撑 `C` 与 `E` 的正式评分
- 在 HTML 详情中展示同日横向对照

### 5.3 参考合约设计原则

第一版必须坚持：

- 主参考是系统自动选出的
- 用户不需要手工传入参考合约
- 参考关系属于系统内部逻辑，不暴露给用户作为输入负担

补充说明：

- 第一版评分主轴已经不再直接围绕“主参考价差 + 邻近参考价差”展开
- 主参考与同日活跃合约集合在第一版中主要用于：
  - 数据组织
  - 辅助解释
  - HTML 详情展示
- 正式评分口径统一以评分设计文档中的 `A/C/E` 为准

## 6. 样本过滤规则

样本过滤仍然保留，因为这是避免误报的基础。

但第一版需要明确：

- 样本过滤的作用首先是“标记状态”
- 不是把样本从结果集中物理删除
- 对于无法分析的样本，系统仍应在结果中保留，并明确说明是“数据不足/对照不足”，而不是“没有异常”

### 6.1 基础数据质量无效样本

以下情况标记为基础数据无效样本：

- `open/high/low/close/pre_close` 任一缺失
- `high < low`
- `open` 不在 `[low, high]`
- `close` 不在 `[low, high]`
- `pre_close <= 0`
- `volume < 0`

### 6.2 极低流动性无效样本

以下情况标记为低流动性无效样本：

- `volume == 0`
- 在已有至少 `10` 个历史样本可看的前提下，过去 20 个交易日中有效成交天数 `< 10`

### 6.3 生命周期边界无效样本

以下样本标记为生命周期边界无效样本：

- `listed_days < 10`
- `days_to_last_trade < 10`

### 6.4 对照不可用无效样本

以下情况标记为对照不足类无效样本：

- 当天没有有效主参考合约
- 主参考合约不通过基础流动性要求
- 当天同品种活跃可分析合约总数 `< 2`

这里的含义是：

- 若连目标合约在内，同日活跃可分析合约总数都不足 `2`
- 则该目标合约无法形成任何有效 peer
- 后续在评分层中统一按“无效样本”处理，而不是继续形成正式候选判断
- 在实现中统一落地为 `sample_status = invalid_insufficient_peer`

### 6.5 历史样本不足无效样本

第一版所有历史窗口统一使用：

- 过去 `20` 个有效交易日
- 不含当天
- 至少要求 `10` 个有效历史样本

若不足：

- 该样本保留在结果集中
- 但统一按“历史不足类无效样本”处理
- 在实现中落地为 `sample_status = invalid_insufficient_history`

## 7. 候选评分体系

第一版评分只服务于：

- 找出值得看的可疑日期

评分体系、子分公式与等级阈值，不再在主设计稿中重复维护。

统一以以下文档为准：

- [2026-06-02-fat-finger-scoring-design.md](/Users/zhangchunfu/Nutstore%20Files/code/python/fat_finger_error/docs/superpowers/specs/2026-06-02-fat-finger-scoring-design.md:1)

主设计稿只保留三条总原则：

1. 评分体系必须服务于“找可疑日期”，而不是直接确认乌龙指
2. 如果某类业务场景分数不合理，应优先修改评分体系，而不是在等级层做补丁
3. 主参考合约自身异常必须是评分体系的正式支持场景，不能被当成特例绕过

## 8. 防误判规则

第一版暂不单独引入独立的 `guard` 机制。

第一版的防误判逻辑统一通过以下三层完成：

1. 样本过滤层的 `sample_status`
2. 评分设计文档中的活跃合约定义与无效样本约束
3. `E` 可信度惩罚分

也就是说，第一版：

- 不再单独维护 `guard` 字段
- 不再引入额外的评分后拦截通道
- 若某类样本业务上应该更高分或更低分，应优先修改评分体系本身

如果后续确实需要加入 `guard`，应作为第二版扩展，而不是在第一版重新引入补丁层。

## 9. 最终输出设计

### 9.1 HTML 报告是主输出

第一版正式输出必须包含：

- `analysis_report.html`

它应该是用户最主要查看的结果。

### 9.2 HTML 报告结构

第一版 HTML 至少包含 4 个区块：

#### 区块 1：总览

显示：

- 分析品种列表
- 开始日期
- 结束日期
- 总可疑日期数量
- 每个品种命中的候选数量

#### 区块 2：品种摘要表

按品种展示：

- 品种编码
- 涉及的候选日期数量
- 涉及的可疑合约数量
- 最高候选分

#### 区块 3：可疑日期明细表

这是报告主体，至少应展示：

- 品种编码
- 合约代码
- 交易日期
- 候选分
- 候选等级
- 触发原因摘要

并支持最基础的交互：

- 排序
- 过滤
- 按品种查看

#### 区块 4：单条详情区

点击某条可疑日期记录后，展示更详细的信息，例如：

- 当天 OHLC
- 当天成交量
- 主参考合约
- 同日活跃合约对照表
- 关键评分项
- `sample_status`
- 数据不足或对照不足原因
- trigger reasons

### 9.3 辅助输出

第一版建议同时输出：

- `suspicious_dates.csv`
- `summary.json`

其中：

- CSV 方便导出与复核
- JSON 方便程序消费

但它们都是 HTML 的辅助输出。

### 9.4 输出目录结构

第一版必须固定单次运行的输出目录结构，避免实现时随意写路径。

建议使用：

- `output/<timestamp>-<symbols>/`

例如：

- `output/20260602_213000-AU_JD/`

目录内至少包含：

- `analysis_report.html`
- `suspicious_dates.csv`
- `summary.json`

如果后续需要补充静态资源，则统一放在该目录下的子目录中。

## 10. 用户最关心的结果字段

系统最终必须围绕人工查看来输出，而不是只输出机器中间字段。

可疑日期结果里，用户最关心的字段至少包括：

- `commodity`
- `contract`
- `trade_date`
- `candidate_score`
- `candidate_level`
- `trigger_reasons`
- `main_reference_contract`

如果后续要补更多字段，也应优先围绕“为什么这一天可疑”来组织。

## 11. 年度风险内容的地位调整

根据当前目标，年度风险不再是第一版核心输出。

新的定位是：

- 如果实现成本低，可以作为附加统计保留
- 如果实现复杂度高，可以放到第二版

第一版不应为了做年度风险而牺牲：

- 可疑日期识别
- HTML 可读性
- 用户入口简洁性

## 12. 第一版实现原则

第一版必须坚持以下原则：

- 用户入口简单：只输入品种编码和时间范围
- 系统自动完成数据拉取和参考构造
- 主结果聚焦在“可疑日期”
- HTML 报告优先于复杂评分体系扩展
- 结论名称与日线证据能力匹配，不夸大

## 13. 后续扩展方向

第一版完成后，可以继续扩展：

- 分钟级确认器
- 逐笔确认器
- 更精细的交互式 HTML 图表
- 年度风险评级体系
- 主连口径扩展
- 日夜盘拆分分析

但这些都不属于第一版必须完成的范围。
